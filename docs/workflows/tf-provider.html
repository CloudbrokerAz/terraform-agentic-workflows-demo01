01

From an API to a shipped provider resource

There is no e2e skill on this track either, so the two halves are joined by you — and here the handoff carries two arguments rather than one, because the design artifact is named per resource.

The human in that top row is doing more work than on the other tracks. Besides approving the design, they are the only thing that carries $RESOURCE from the first invocation to the second: it appears in the design filename but not in the branch name, so a forgotten second argument breaks the design-exists check at the start of the implement half.

02

The runtime spine, and the lane that is not there

Thirty-four steps across two lanes, expanded from the shortest pair of skill files in the repo — 23 numbered steps against the module track’s 26. The third lane is drawn empty because this track has no harness at all.

The TDD loop here never turns red to green. It turns non-compiling to compiling. The test-writer emits every acceptance test with t.Skip("not implemented") over a commented-out skeleton, and the only verification the track performs on those tests is go test -c -o /dev/null — which builds the test binary and throws it away.

03

What each actor knows

Seven reference skills, and a distinct family from every other track — the provider-* skills rather than the tf-* ones.

Two cells are worth reading against each other. provider-run-acceptance-tests is loaded by the validator alone — the one agent positioned to run them, and the one the orchestrator never asks to. And the validator is the only test-touching agent that does not load provider-test-patterns, so it judges test structure against the constitution rather than against the skill that generated the tests. It now also loads tf-judge-criteria, the shared rubric the other three tracks score against; until recently it was the only validator that did not.

04

Three reasons no acceptance test ever runs

The track ships a complete acceptance-test scaffold. Three independent things stop any of it executing, and removing any one of them would not be enough.

The guard layer cannot compensate, because it is equally blind here. A .go write matches no branch in the fix hook and receives only a trailing-newline repair; at the turn boundary validate.sh and lint.sh build their file set from a *.tf glob and exit 0 on the empty set; trivy config is an IaC misconfiguration scanner and does not read Go. Searching scripts/hooks/ for go build, gofmt or staticcheck returns nothing. The net enforced guarantee for a provider turn is a trailing newline and a private-key grep — every Go quality gate exists only as agent prose.

05

What differs from the module track

Same skeleton, different language, and a materially different level of assurance.

01languageGo under internal/service/<service>/ using the Plugin Framework. The verification vocabulary is gofmt, go build, go vet, staticcheck — none of which any hook runs.
02two argumentsprovider-design-{resource}.md is the only design artifact whose filename carries a second identifier, and it propagates through the whole call shape.
03toolchain gateThe only track that gates on a language runtime — go version, Go ≥ 1.21 — though only at plan time; implement never re-checks.
04two-stage gateThe only track that gates on a language runtime, now at both plan and implement time.
05research toolsWebSearch and WebFetch instead of the terraform MCP server — reasonable, since registry and workspace tools cannot help author Go. The test-writer has neither — the only agent on the track without both.
06testsCompile-only. The module track executes terraform test after every checklist item and again at the end; nothing here ever executes a test.
07fix loopCapped at three rounds, matching every sibling track.
08report ownerInverted: the orchestrator writes the validation report, where the module validator writes its own.
09PRNo semver:* label and no label bootstrap.
10measurementNo e2e skill, no eval cases, no judge — though the harness is closer than it looks: the case schema already lists provider as a track and a Provider rubric already exists.
06

Findings

Produced by an independent review pass over the same source files, then verified against the code. Four further findings — the missing plan step, unrecoverable $RESOURCE, the uncapped fix loop and the overstated parity in AGENTS.md — were fixed at source rather than documented here.

High

The acceptance-test suite still does not run by default

One of the three blocks in Fig. 3 is now gone: the skill’s step 10 carries a real command, states the credential precondition, and explains that a green run with every test skipped is not a passing suite. The other two stand. Acceptance tests remain opt-in — deliberately, since they provision billable cloud resources — and the test-writer still emits every function with t.Skip, with nothing anywhere verifying that a single skip was removed.

So the default outcome is unchanged — a complete, compiling, correctly-structured test suite that asserts nothing — but it is now a documented choice with an escape hatch rather than a dead four-word instruction.

High

The guard layer enforces nothing on a Go codebase

Verified three ways: the fix hook branches only on *.tf|*.tfvars and *.yaml|*.yml, so a .go write gets a trailing newline; validate.sh and lint.sh exit 0 on an empty *.tf set; and grepping scripts/hooks/ for go build, go vet, gofmt, golangci or staticcheck returns no matches.

Combined with the absence of an eval harness, no automated mechanism at any layer confirms that a provider run compiled, vetted cleanly, or passed anything.
