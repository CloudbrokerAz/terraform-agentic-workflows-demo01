What actually runs

The consumer track’s sibling of the module harness — and the one that stands real infrastructure up. A 43-line skill file reaches four subagents, eight reference skills and four guard hooks, deploys to an HCP Terraform sandbox, and relies on something outside itself to tear that sandbox down again.

01

From a request to live infrastructure

You invoke two orchestrating skills in turn; they dispatch four subagents, with one more kept deliberately outside. One agent fewer than the module track — there is no test-writer, because this track proves itself by deploying rather than by testing.

Two of these agents are shaped by a constraint the module track does not have. The design agent holds zero MCP tools by design, so every fact about a private registry module reaches it second-hand through research-*.md — the research lane is the only thing standing between the design and invented module inputs. The validator inspects a live cloud run, not just files: it is handed a run ID and workspace name and queries HCP Terraform directly, and unlike its module counterpart it is forbidden from fixing anything it finds.

02

The runtime spine

Twenty-nine steps across three tiers. Eleven belong to the harness — four before the session starts and seven after it ends — and everything that guarantees the sandbox does not survive lives in that second group.

Both tracks run the same run-eval.sh; it contains no track branching, and forks only on whether the case asks for a deployment. What the consumer track adds is all cloud lifecycle: harvesting the HCP Terraform run facts, destroying the workspace through teardown-sandbox.sh, and merging that destroy result back into the verdict so a run which cannot prove it cleaned up cannot pass.

03

Three destroys, one guarantee

This is the difference that matters. From step 17 the run owns billable cloud resources. Three separate mechanisms can destroy them, and only the last one always does.

The project’s own notes say eval runs “always destroy consumer sandbox deployments”. That is true — but it is true of the harness, not of the workflow. Read only the skills and you would conclude teardown is an optional question asked after the pull request is already open. Anyone reasoning about cost exposure needs to know which of the two paths they are on: a human running /tf-consumer-implement directly gets the opt-in prompt and nothing else behind it.

The harness earns the guarantee three ways. The trap is armed before the repo is provisioned, so even a failure during setup tears down. INT and TERM are routed through exit 130 rather than handled in place, because a non-exiting handler would resume the script with teardown already marked done and silently leak later deploys. And destroy_clean is deliberately left out of the deterministic checks and merged afterwards, with a branch that hard-fails when a deploying case produces no destroy result at all.

04

What each actor knows

Reference skills are preloaded through agent frontmatter rather than requested at runtime — one orchestrator aside, which loads its taxonomy from its own body. Eight skills, and the most telling thing about them is which one is missing.

Two cells carry the track’s identity. tf-runtask is loaded by nothing on the module track — it exists so the validator can read HCP Terraform run task results off a live deployment. And where the module matrix shows terraform-test shared by the design and test-writer agents, here the column does not exist at all: no actor on this track holds any test-authoring knowledge, which is the frontmatter-level consequence of having no test-writer.

05

What differs from the module track

The two harnesses are structurally twins and behaviourally quite different. If you have read the module page, these are the deltas that matter.

01agent rosterFour subagents, not five. It is the only one of the four workflows with no test-writer — no tf-consumer-test-writer.md exists.
02no tests at allThe developer states the rule outright: the consumer workflow does not write .tftest.hcl files. Validation is terraform validate plus a real deployment.
03proof of correctnessThe module track proves itself by failing tests first. This track proves itself by standing the infrastructure up and scoring the run.
04deploy and destroyConsumer only. All six cases set sandbox.deploy=true; both module cases set it false and have no workspace at all.
05checklist sectionSection 5 of six, not Section 6 of seven. The single easiest thing to get wrong moving between the two.
06deterministic checksAn exact one-for-one swap: destroy_clean here, terraform_test there. The other eight are identical.
07private registryModule composition is enforced at five layers — a mandatory clarification question, a research lane, the design rule, the developer’s five-glue-resource limit, and a validator conformance check.
08clarification gateUp to five questions with four mandated topics, against four questions and one mandated topic on the module side.
09env gateAdds an MCP list_terraform_orgs call to prove the token works before anything deploys. Present in the plan skill only.
10validator powersGiven a run ID and workspace name and three HCP MCP tools; inspects a live run and is explicitly non-destructive, where the module validator auto-fixes.
11rubric weightingSame tf-judge-criteria skill, different table: Module Usage 25%, Security 30%, Code Quality 15%, Variables 10%, Wiring 10%, Constitution 10%.
12eval coverageSix prompts, six cases, one to one — the reverse of the module track, which ships eight prompts and grades two.
06

Findings

Produced by an independent review pass over the same source files, then verified against the code.

Medium

Only prompt text links the workspace the run creates to the one the harness grades

No skill and no agent calls create_workspace, and none needs to: the Terraform CLI creates the HCP Terraform workspace from the cloud{} block’s organization, project and name on init or apply. That is the documented mechanism, not a gap. It is why the project attribute is grepped twice — once entering Phase 3 and again immediately pre-deploy — since the block is the only place the workspace’s project is decided, and getting it wrong silently lands the workspace in Default.

What is unguarded is the coupling. The name the design chooses and the workspace_pattern the harness expects are joined by nothing but prompt text substituted at render time, and no step asserts they agree. Let them drift and the run still succeeds — against a workspace the harness is not looking at.

Medium

The Section 5 gate is the weakest of three assertions on the same fact

Three layers check that the implementation checklist is complete, at three different strictnesses. The orchestrator accepts “flag the gap” as a resolution, so Phase 4 can proceed with unchecked items. The e2e skill demands every item be [x]. The harness runs checklist_complete as a hard deterministic check. The layer closest to the work is the one that can be talked out of it.

Low

Outside the harness, nothing guarantees the sandbox is destroyed

The workflow’s own teardown is implement:55 — an interactive “Destroy sandbox resources?” placed after the pull request, with no finally semantics, no cleanup on failure paths and no budget guard. A human who runs /tf-consumer-implement and then closes the terminal, or whose run dies at any point between the apply and that question, leaves live billable infrastructure with nothing else scheduled to remove it.

Inside the harness this is fully covered by the EXIT trap. The gap is only in the direct-invocation path — which is exactly the path a developer takes when trying the workflow for the first time.

Low

Subagents are not Stop-gated

There is no SubagentStop entry in .claude/settings.json, so tf-guard verify never runs when a developer or validator subagent returns — only when the top-level orchestrator tries to end a turn. Findings therefore surface late and in aggregate, attributed to the orchestrator rather than to the subagent that caused them.

Low

The developer cannot re-verify a module’s interface

tf-consumer-developer holds search_private_modules but not get_private_module_details, so at implementation time it can find a private module but cannot check its exact input and output types. That verification exists only in the research agent, whose findings reach the developer indirectly through consumer-design.md.
