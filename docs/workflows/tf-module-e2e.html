01

Who calls whom, and where the hooks fire

Two orchestrating skills, five in-workflow subagents and one deliberately kept outside. Every subagent starts with a fresh context, so what they share is only what is on disk — chiefly design.md, which every implementation agent reads — and every file any of them writes passes through guard hooks that no skill file mentions.

Three properties are worth pulling out. The test-writer has no Bash tool, so it physically cannot run terraform — the tests it writes are shaped by design.md Section 5 alone, not by what happens to pass. The developer runs once per checklist item and ticks its own box, which is why the Section 6 gate exists at all. The judge shares no context with the run and is explicitly forbidden from opening the validator’s report, so its score cannot be anchored to the workflow’s own self-assessment.

The Stop hook is the most consequential of the four. It re-runs validate, tflint and trivy at every turn boundary for the whole session — nothing scopes it to the workflow — duplicating much of what the validator agent does in Phase 4. validate and tflint run over git diff HEAD plus untracked files, so their scope widens as the session accumulates changes; trivy scans the entire repository regardless. The practical effect is that quality enforcement here is doubled up in one environment and, because every check exits 0 silently when its binary is absent, entirely absent in another.

02

The runtime spine

Thirty-one steps across three tiers. The eval harness brackets the run at both ends; the skill itself owns only the thin middle. Two of the four gates are bypassed.

The shape matters more than the individual steps. The harness owns both ends, and the skill never learns that it exists — the only channel between them is a prompt file whose text happens to name the skill. Everything between step 4 and step 28 would run identically if a human typed the command.

03

What each agent knows

Reference skills are preloaded through agent frontmatter rather than requested at runtime — one orchestrator aside, which loads its taxonomy from its own body. The matrix is sparse on purpose: each actor gets exactly the knowledge its phase needs and nothing else.

tf-domain-category is the only reference skill an orchestrator loads directly; everything else arrives through an agent’s frontmatter. The consequential cell is tf-judge-criteria, loaded by both the in-workflow validator and the out-of-band judge. The eval’s independence therefore comes from fresh context and read-only tools, not from a different standard — both sides score against the same six weighted dimensions and the same Security below 5.0 → not production ready override.

04

Findings

Produced by an independent review pass over the same source files, then verified edge by edge against the code.

Low

The module track has a third of the eval coverage the consumer track has

The consumer track wires all six of its prompts to cases, one to one. The module track ships eight prompts and two cases — only example_s3.md and example_bedrock_agentcore.md are graded. The other six are runnable by hand (/tf-module-e2e example_ec2) but nothing scores them.

Not obviously a defect: each case carries per-prompt judge assertions that have to be written from that prompt's requirements, and every added case doubles down on suite cost. The committed suite — two module cases plus the consumer track’s six — looks like a deliberate trade-off — it is just nowhere recorded as one, which is why the gap reads as an oversight.

Both committed module cases also set sandbox.deploy=false, so the module track never provisions real infrastructure; deploy and teardown are exercised by the consumer track alone. That is by design — the module workflow is verified through terraform test and static analysis.
