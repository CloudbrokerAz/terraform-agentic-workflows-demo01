tf-policy
What actually runs

Plan and implement for the tfpolicy track. Five subagents, six reference skills and the strictest quality gate in the repo — a failing validation genuinely blocks the pull request. And almost none of it is verifiable, because nothing outside the agent session ever checks that the policy engine ran.

01

From a compliance rule to an enforced policy set

There is no e2e skill on this track, so nobody automates the two halves into one run — you do. You invoke the plan skill, answer its questions, approve the design, then invoke the implement skill. That makes the human approval gate a real gate rather than something a prompt file waves through.

This is the same five-agent shape as the module track, with one structural consequence of having a person in the loop: the approval gate between the halves genuinely stops the run. On the module and consumer e2e paths it is skipped, because a prompt file has already answered it. Here nothing proceeds to code until you say so.

02

The runtime spine, and the lane that is not there

Twenty steps across two lanes. The module and consumer tracks have a third — an eval harness that provisions a repo, re-runs the gates independently and grades the result. This track has nothing above the orchestrator at all.

The shape is the module track minus its measurement. Everything from the ambiguity scan through the validator is present and in places stricter — but the row of checks that would confirm any of it happened is absent, and so is the independent judge that would score the result without sharing the agent’s context.

03

What each actor knows

Six reference skills. The tf-policy skill — the engine reference — is loaded by four of the five agents, which is what keeps the track’s syntax consistent without any tool enforcing it.

One cell is missing rather than present. tf-research-policy-azure ships as a skill alongside its AWS twin, but no agent preloads it and tf-policy-research hard-codes the AWS one — so the Azure research path exists as a document and is unreachable from the workflow.

04

The guard layer is blind to this track

The same four hooks fire as on the module track. On a turn that writes only .policy.hcl and .policytest.hcl, almost none of them do anything.

05

What differs from the module track

The two tracks are the same skeleton. These are the deltas worth knowing.

01artifactDeclarative guardrails — policies/<domain>.policy.hcl paired with a same-named .policytest.hcl — rather than the infrastructure itself.
02enginetfpolicy validate and tfpolicy test replace the terraform trio. The engine is hard-locked: a request for a different one is routed to the constitution, not treated as a clarification.
03blockingStricter than the module track in one important way — a validation still FAILing after three rounds does not open a PR. The module track opens one regardless.
04clarificationThree of four question slots are mandated, against one of four on the module side.
05upstream reuseA compliance-driven mode auto-discovers the YAML rule set produced by tf-research-policy-aws and threads it through research and design. No other track reuses an upstream artifact.
06test-writerBash-less on both tracks, but it bites harder here: tfpolicy test is the only signal that the design’s scenarios were transcribed correctly.
07toolchain gateBoth tracks now gate on their engine — tfpolicy version here, go version on the provider side — so a missing binary stops the run up front rather than mid-loop.
08PRNo semver:* label and no label bootstrap — the module track needs both because its CI blocks unlabelled PRs.
09measurementNo e2e skill and no eval case, so the track-agnostic harness and judge are never pointed at this track, and deterministic.sh has no tfpolicy check. The decisive asymmetry.
06

Findings

Produced by an independent review pass over the same source files, then verified against the code. Three further findings — an unreachable Azure research path, a missing engine gate and an undefined carve-out in the per-item gate — were fixed in the skills rather than documented here.

High

Nothing outside the agent verifies the policy engine ran

The string tfpolicy appears nowhere in scripts/hooks/. Two of the four Stop checks — terraform validate and tflint — build their file set from a *.tf glob and exit 0 on the empty set. trivy config still scans the repo but cannot parse policy HCL. So on a policy-only turn the only check that reads the new files is the private-key grep. There is no eval case for this track and no tfpolicy check in deterministic.sh either, so nothing re-runs the engine independently — even though the harness, judge and rubric already exist and already accept track: "policy".

The consequence is that tfpolicy validate and tfpolicy test passing is an assertion made by the agent about its own work. On the module track the same claim is checked twice more — by the Stop hook and by the harness. Here it is checked nowhere.

Medium

The plan skill contradicted itself about its own output filename

tf-policy-plan called its design artifact tf-policy-design.md in the frontmatter description and the opening line, but policy-design.md in step 9 and again on the Done line — two names for one file inside a 47-line skill. The design agent writes policy-design.md, and all four downstream readers — test writer, developer, validator and the judge criteria — open that same path, so the working name was the correct one and the description was the outlier.

Nothing broke at runtime, because the name that appears in the frontmatter is never resolved as a path. The cost was to the reader: the two places a human looks first to learn what the skill produces both named a file that does not exist. Resolved in 059c238 by standardising on policy-design.md at all four sites.
